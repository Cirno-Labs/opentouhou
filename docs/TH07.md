# th07

Notes on how 東方妖々夢 ~ Perfect Cherry Blossom is structured and how
its parts map onto opentouhou. The overall design is in
[ARCHITECTURE.md](ARCHITECTURE.md). Where th07 works as th06 does,
[TH06.md](TH06.md) applies.

## Source

The port is written from [Cirno Labs' th07
decompilation](https://github.com/Cirno-Labs/th07) at commit a67fa35,
where all 694 game functions match the retail 1.00b executable. That
code is MSVC 7 C++ in the style of the th06 decompilation, and it uses
the th06 decompilation's names for the classes and members that the two
games share, so a file of one compares directly with the file of the
same name in the other. Its hook DLL (`src/dll/`) is not part of the
port. File names below refer to the decompilation's `src/`.

## Game speed

th07 can run its gameplay slow. Two ECL pattern functions,
StartSlowdown and EndSlowdown (`unsorted417af0.cpp`), set the game speed
to `1/n` and back to 1; the retail scripts of stages 5, 6, Extra and
Phantasm call them 40 times. While the speed is below 1, frame counters
advance by fractions of a frame (`Timer::Add`, `App::TickTimer`) and
bullets, lasers, items and bombs move at that speed. Replays play
through these slowdowns, so the game speed is simulation state, and the
port keeps the fractions: `stg/timer` counts them in single precision,
as the original does.

th07 has no refresh-rate scaling like th06's (TH06.md, "Game speed"): only
these ECL functions change its game speed, and the menus and every new
game set it back to 1.

## Audio

- Sound effects: WAV files in `data/wav`, played as in th06.
- Music: one file of raw PCM tracks, `thbgm.dat`, beside `th07.dat`.
  `bgm/thbgm.fmt` in the archive lists where each track is, its format
  and its loop. The original plays MIDI when `thbgm.dat` is missing; the
  port drops MIDI and needs the file.

## Replays

### Capturing replay test cases

`just replay::build th07` builds `th07capture.exe` and
`th07capture.dll` in `build/replay/th07/`, and `just replay::capture
th07` runs them as it runs th06capture. They take th06capture's
command line and work as it does (TH06.md, "Capturing replay test
cases"), with these differences:

- the game is retail 1.00b `th07.exe`, its config `th07.cfg`, and the
  replay copy `replay/th7_ud0000.rpy`. The default `--out` is
  `../opentouhou-cases/th07`;
- `--fast` also runs QueryPerformanceCounter without real time, since
  th07 paces its frames with it;
- a replay plays as the replay menu plays it with normal speed. A
  Phantasm replay starts as stage 8;
- a case ends with the last calc before the game leaves gameplay. On
  the title screen, the original's game state holds uninitialized
  memory;
- th07capture.dll finds its patch sites at start-up, in the functions
  that `replay/th07/retail.h` names, and stops the game when one is not
  found exactly once.

### Running replay test cases

`th07replay` plays a case's replay against the port, built on
[ARCHITECTURE.md](ARCHITECTURE.md)'s shared runner. It keeps the
replay under `scratch/` plus the input file's own name, so a resave
never writes over the file the case points at. A replay's slot 7 plays
stage 7 for Extra and stage 8 for Phantasm, as `RunnerReplay_GetStage`
maps it; the runner checks the last stage's calc count against the
case's row count, with one calc of slack for the capture's own last
calc out of gameplay (`RUNNER_END_WITH_PLAY`, core/runner.h).

A matching case proves parity with retail playback. The runner
disables the optional replay_desync fix. A case can also match a
retail desync or an early game over. It does not prove that the
recording reaches its saved score or its final stage.
