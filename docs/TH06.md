# th06

Notes on how 東方紅魔郷 ~ the Embodiment of Scarlet Devil is structured
and how its parts map onto opentouhou. The overall design is in
[ARCHITECTURE.md](ARCHITECTURE.md).

## Source

The port is written from [Cirno Labs' th06
decompilation](https://github.com/Cirno-Labs/th06) at commit a91710a,
where all 511 game functions match the retail 1.02h executable. That
code is MSVC 7 C++ for 32-bit Windows, Direct3D 8, D3DX8, DirectSound,
DirectInput 8, winmm and GDI. It is "C with classes": a few hundred
member functions, a handful of virtual functions (almost all in the
DirectX SDK sound helpers, which go away), almost no templates. Its hook
DLL (`src/dll/`) and its standalone exe's optional features (`src/exe/`)
are not part of the port. File names below refer to the decompilation's
`src/`.

## The task chain

th06 runs on `Chain` (`chain.h`): two priority-ordered
lists of callbacks, one for updates and one for drawing. Lower priority
runs first. Each frame (`unsorted41f230.cpp`, the window's frame
function) the original:

1. Clears the back buffer, if the configuration makes it clear.
2. Runs the whole draw chain, unless frame skipping skips this frame.
3. Runs the whole update chain.
4. Plays the sounds queued during the update.

So what a frame shows is the state *before* that frame's update.

Each element holds a callback, optional added and deleted callbacks, and
an argument. An update callback's return value decides what happens next:

| Return | Effect |
| --- | --- |
| 0 | remove the element, continue |
| 1 | keep the element, continue |
| 2 | run the same callback again |
| 3 | stop, and the chain returns 1 |
| 4 | stop, and the chain returns 0 |
| 5 | stop, and the chain returns -1 |
| 6 | start over from the first element |

The draw chain uses the same codes, except that it never starts over.

The port keeps the chain, its ordering and its return codes, because
gameplay depends on them. What changes:

- The game's step runs the draw chain and then the update chain, in the
  original's order, because draw callbacks have side effects the update
  may see. Draw callbacks record into the `FRAME` instead of calling
  Direct3D.
- The update chain's result can end the frame loop: 0 quits, and -1
  tears everything down and starts again, which the original does when
  an option that needs a restart (such as the display mode) changed. The
  port quits on 0 and applies such options without restarting.
- Draw callbacks are not pure (some advance animation state), which is
  why they run once per tick rather than once per display frame.
- Frame skipping (`frameSkip` in the configuration) skips the draw chain
  on some ticks, and with it the draw callbacks' side effects. Whether
  any of those reach gameplay, and so whether replays depend on the
  frame-skip setting, has to be checked during the port. The native port
  has no reason to skip drawing, but it may have to keep running the
  draw chain's side effects on skipped ticks to stay replay-exact.
- The chain's leftovers from the original (`midiOutDevs`, the unused
  space up to the logger) go away.

## Simulation state

The original keeps its game state in a few dozen globals
(`g_GameManager`, `g_Player`, `g_BulletManager`, `g_Chain`, ...). How
the port stores them is decided when it reaches them; the determinism
rules in [ARCHITECTURE.md](ARCHITECTURE.md) apply either way.

## Floating point

th06 ran on the x87 FPU with its precision control set to 24 bits:
Direct3D 8 does that when a device is created without
`D3DCREATE_FPU_PRESERVE`, and th06 creates it that way. So:

- Float arithmetic rounded like IEEE single precision, which SSE float
  arithmetic reproduces (outside extended-exponent edge cases, checked
  where they can occur).
- Arithmetic the source writes as `double` was also rounded to single
  precision. In the port it is computed as `float`.
- `fsincos` and `frndint` appear as inline assembly (`SinCos`, `Rint` and
  others in `unsorted.h` and `sprite.h`); `core/math` provides
  replay-exact equivalents, as it does for `_ftol` truncation and the
  D3DX8 vector and matrix functions th06 calls.
- D3DX8 picks CPU-specific code paths at runtime. The port reproduces the
  path the replay corpus was recorded against.

## Random numbers

All gameplay randomness comes from one generator, `g_Random`
(`Rng`, `unsorted.h`): a 16-bit seed, 16 random bits per step, 32-bit
values from two steps, and floats and ranges built on those. Replays
store the seed each stage starts with (`ReplayStage::rngSeed`). The
generator moves into the simulation state unchanged.

## Rendering

What th06 needs from `core/gfx`:

- Views: the 3D stage background through one camera, the playfield and
  the HUD through others.
- Depth: test functions `LESSEQUAL` and `ALWAYS`, writes switched on and
  off independently.
- Fog: `D3DFOG_LINEAR` as table (per-pixel) fog, with start, end and
  colour from the stage.
- Texture transforms: a 2-component texture matrix, for scrolling.
- No lighting (`D3DRS_LIGHTING` is off).
- Texture stages:

  | Colour or alpha | Operation | Arguments |
  | --- | --- | --- |
  | both | `MODULATE` | texture, diffuse |
  | both | `SELECTARG1` | texture, or diffuse |
  | colour | `ADD` | texture, diffuse |
  | both | as above, with `TFACTOR` | a constant colour instead of diffuse |

- Blending: source alpha over inverse source alpha, or additive. Gouraud
  and flat shading.
- Images: ANM entries can take a texture's alpha from the blue channel of
  a second image. Textures were created in 16-bit formats (`A1R5G5B5`,
  `A4R4G4B4`, `R5G6B5`) in 16-bit colour mode.
- The HUD frame is redrawn only for a few frames after it changes
  (`redrawFrames`); the original relies on the back buffer keeping its
  contents in between. The port redraws it every frame, as thcrap's
  `hud_force_redraw` does.
- Title and result backgrounds are copied onto the back buffer with
  `CopyRects`; in the port they are textured full-screen quads.

## Audio

- Sound effects: WAV files, played through DirectSound buffers with
  per-sound volumes.
- Music: one WAV file per track in `bgm/`, streamed. The original's MIDI
  mode is dropped.

## Slowdown statistic

The result screen shows a "slow rate", which the original computes from
the frame rate it measures with `timeGetTime` (`DrawFps`). The port takes
the measurement from `core/app` as a per-tick value, which replays record.

## Replays

The 17 world-record replays collected in the decompilation's repository
are the replay test corpus for th06 (see
[ARCHITECTURE.md](ARCHITECTURE.md), "Testing").

### Capturing replay test cases

`just replay::build th06` builds `th06capture.exe` and
`th06capture.dll` in `build/replay/th06/`:

```sh
wine th06capture.exe --game <dir> (--replay <file.rpy> | --live) \
    [--dry-run] [--fast] [--quit-after <seconds>] [--out <dir>]
```

th06capture.exe checks that the game is retail 1.02h, starts it with
th06capture.dll loaded, and prints the DLL's log. The DLL:

- sends every file the game writes to a temporary work directory, so
  the game directory stays unchanged (`replay/core/overlay.c`);
- makes timeGetTime count from 0. The original's frame wait computes in
  single precision and never ends after a few days of uptime;
- with `--replay`, starts that replay from the title screen as the
  replay menu does, and closes the game when the replay ends;
- from the first calc of play (not the title's demo) until the game
  exits, writes a replay test case (`replay/core/case.h`), one row per
  calc, to `--out` (default `../opentouhou-cases/th06`). It is named
  after the replay, or `live-<date>-<time>.otrc`.

The work directory holds a fixed `東方紅魔郷.cfg` (windowed, no frame
skip, no sound) and, for `--replay`, the replay as
`replay/th6_ud0000.rpy`. `--dry-run` loads the DLL and ends the game
before it runs, so it writes no case. `--quit-after` closes the game
after that many seconds; it cannot combine with `--fast`. `--fast` runs
every frame wait without waiting for real time, for `--replay` only.

`overlay_test.exe` checks the overlay without the game: run it in an
empty directory with another empty directory as its argument.
